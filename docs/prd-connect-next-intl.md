# PRD: Подключение i18n (next-intl)

**Дата**: 2026-09-09
**Статус**: Draft

## Цель

Сделать интернационализацию реально рабочей, как заявлено в ТЗ: сейчас `next-intl` установлен, но не подключён — в `next.config.ts` нет плагина, нет языкового сегмента в роутинге, а все строки интерфейса захардкожены в компонентах. Нужно вынести пользовательский текст в файлы локализации и обеспечить работу русской локали через механизм локализации, сохранив архитектурную готовность к добавлению английского языка.

## Пользовательские сценарии

- Пользователь открывает любой экран → весь текст приходит из файлов локализации, а не из кода компонентов.
- Разработчик добавляет новую строку интерфейса → меняет только файл локализации, не трогая компоненты.
- (После добавления второго языка) Пользователь переключает язык → интерфейс, даты и числа переключаются без изменения кода страниц.

## В скоупе

- Фактическое подключение `next-intl` к приложению (провайдер, конфигурация, русская локаль по умолчанию).
- Вынос всех захардкоженных пользовательских строк из страниц и компонентов (`app/*`, `components/*`) в `messages/ru.json`.
- Приведение `messages/ru.json` к UTF-8 и синхронизация его структуры с фактически используемыми ключами.
- Форматирование дат и чисел через механизмы локализации там, где они выводятся пользователю.
- Правило для проверки: в JSX/компонентах не остаётся кириллических строковых литералов, отображаемых пользователю.

## Не в скоупе

- Добавление английского языка и переключение локалей в UI (последующая итерация, для которой эта работа создаёт фундамент).
- Перевод контента, генерируемого вне UI (например, шаблон PDF-экспорта).
- Локализация системных сообщений Supabase/ошибок валидации сторонних библиотек.

## Технические ограничения

- Проект на Next.js 16.2.3: конвенции App Router для интернационализации отличаются от Next.js 14 из ТЗ — сверяться с докой в `node_modules/next/dist/docs/` и учитывать deprecation-предупреждения.
- `messages/ru.json` и `i18n/request.ts` уже существуют (последний хардкодит `locale: "ru"`), но не используются кодом.
- `lib/i18n.ts` экспортирует хуки-обёртки, однако вызовов `useTranslations` в коде нет.
- Файлы `messages/ru.json`, `app/layout.tsx` и ряд компонентов сейчас в cp1251 (см. PRD «Стабильность и техдолг»).

## Критерии готовности

- [ ] Приложение запускается (`npm run dev`) и работает с включённым `next-intl` без ошибок и deprecation-предупреждений.
- [ ] Поиск по коду не находит кириллических строковых литералов в отображаемом тексте страниц и компонентов (исключение — только файлы локализации).
- [ ] `messages/ru.json` — валидный UTF-8 JSON, содержит ключи для всех экранов: лендинг, авторизация, дашборд, конструктор (5 шагов), результат, настройки, админка, тарифы.
- [ ] Русская локаль — локаль по умолчанию; отображение экранов не отличается от текущего (текст тот же, что был хардкодом).
- [ ] Даты и числа на экранах результата/дашборда форматируются согласно локали.
- [ ] Отсутствие ключа локализации приводит к видимому предупреждению в dev-режиме (то есть механизм реально используется, а не подменён).
