# PRD: Монетизация Pro/Business

**Дата**: 2026-09-09
**Статус**: Draft

## Цель

Превратить страницу тарифов из витрины в источник дохода: дать пользователям возможность купить планы Профессиональный (99 у.е./мес) и Бизнес (299 у.е./мес), описанные в ТЗ. После оплаты у пользователя меняется тариф, расширяются лимиты (проекты, кастомные сервисы) и снимается водяной знак с PDF. Цель — проверить гипотезу платности на реальных пользователях.

## Пользовательские сценарии

- Пользователь на `/pricing` видит карточки с активными кнопками (сейчас «Скоро», disabled) → выбирает план и оплачивает.
- Пользователь оплатил Профессиональный → тариф становится `pro`, лимит проектов 20, до N кастомных сервисов, экспорт PDF без водяного знака; на дашборде и в `/pricing` отображается актуальный план.
- Пользователь оплатил Бизнес → безлимитные проекты (практический лимит задаётся отдельно).
- Пользователь отменяет подписку → после окончания оплаченного периода тариф возвращается к `free`, лимиты и водяной знак возвращаются.
- Сбой оплаты/прерванный платёж → пользователь остаётся на `free` с понятным сообщением, данные проекта не теряются.

## В скоупе

- Выбор и интеграция платёжного провайдера (кандидат — Stripe): создание платёжной сессии, обработка результата оплаты, управление подпиской и её отменой.
- Webhook-обработка событий подписки с проверкой подписи и идемпотентностью.
- Новый объект данных для подписки (сейчас тариф — просто колонка `subscription_tier` в `profiles`, привязать подписку к платежам без отдельного объекта нельзя) + миграция.
- Активация кнопок на `/pricing`, отображение актуального плана и даты окончания подписки.
- Применение лимитов и водяного знака на основе тарифа в существующих проверках (лимит проектов, кастомные сервисы, PDF).

## Не в скоупе

- Мультипользовательский доступ для Бизнес (в ТЗ — перспектива).
- Годовые скидки, промокоды, инвойсы и налоговые документы.
- Пробный период и понижение тарифа «на лету» с сохранением данных сверх лимита (только блокировка создания нового).
- Локализация платёжных страниц провайдера.

## Технические ограничения

- Валюта не определена: ТЗ оперирует «у.е.» — требуется продуктовое решение о реальной валюте и ценах до интеграции.
- Провайдер оплаты требует аккаунта, публичных/секретных ключей и публичного HTTPS-endpoint для webhook — зависимость от деплоя (PRD «Стабильность и техдолг»).
- Схема БД сейчас содержит 8 таблиц без объекта подписки; изменения — только миграциями в `supabase/migrations/`.
- RLS: данные подписки пользователя видны только ему, администратору — все (по аналогии с существующими таблицами).
- Тестовый режим провайдера обязателен до боевых платежей.

## Критерии готовности

- [ ] Тестовая оплата плана Профессиональный (тестовый режим провайдера): тариф пользователя становится `pro`, лимит проектов — 20, экспорт PDF без водяного знака (проверено на реальном проекте).
- [ ] Тестовая оплата Бизнес: тариф `business`, создание проектов не ограничивается лимитом `free`.
- [ ] Событие отмены/окончания подписки из webhook возвращает пользователя на `free`, лимиты и водяной знак восстанавливаются.
- [ ] Webhook обрабатывает события идемпотентно (повторная доставка не дублирует изменения) и с проверкой подписи.
- [ ] Кнопки на `/pricing` активны; после оплаты карточка показывает «Текущий тариф», у пользователя нет возможности оплатить уже активный план повторно.
- [ ] Прерванный/неудачный платёж не меняет тариф; пользователь видит понятное сообщение об ошибке.
- [ ] `npm run lint` и `npx tsc --noEmit` проходят; миграция применена, RLS для данных подписки проверена от имени пользователя и администратора.
