# Plan: Стабильность и техдолг

**PRD:** [docs/prd-stability-and-technical-debt.md](prd-stability-and-technical-debt.md)
**Дата:** 2026-09-09

## Фазы реализации

### Фаза 1: Исправление кодировки текста

**Цель:** русский текст во всех экранах и в `messages/ru.json` отображается корректно; появление cp1251-файлов впредь отлавливается автоматически.
**Затрагивает:** frontend
**Задачи:**
- [ ] Перекодировать в UTF-8 10 файлов в cp1251: `app/layout.tsx`, `app/page.tsx`, `app/pricing/page.tsx`, `app/api-docs/page.tsx`, `components/layout/header.tsx`, `components/auth/sign-in-form.tsx`, `components/auth/sign-up-form.tsx`, `components/builder/wizard-layout.tsx`, `components/builder/step-summary.tsx`, `messages/ru.json`.
- [ ] Проверить остальные файлы с русским текстом на соответствие UTF-8 и перевести найденные в cp1251.
- [ ] Добавить команду/скрипт проверки: все `.ts/.tsx/.json` с русским текстом декодируются как UTF-8.
- [ ] Визуально проверить экраны `/`, `/login`, `/register`, `/pricing`, `/api-docs`, все шаги конструктора и дашборд на отсутствие mojibake.
**Тесты:** автоскрипт проверки кодировки даёт «0 найденных»; `npm run lint` и `npx tsc --noEmit` проходят после перекодирования.
**Когда готова:** критерии готовности PRD №1 и №2 — скрипт не находит файлов вне UTF-8 (включая 10 из перечня), на всех перечисленных экранах нет «кракозябр».

### Фаза 2: Наведение порядка в репозитории и документации

**Цель:** вся реализация сохранена в git, README соответствует реальному проекту, документация не противоречит схеме БД.
**Затрагивает:** инфраструктура (git, документация)
**Задачи:**
- [x] Закоммитить неотслеживаемую реализацию (`app/`, `components/`, `lib/`, `i18n/`, `messages/`, `supabase/`, `middleware.ts` и пр.).
- [x] Привести README к реальному состоянию: запуск, переменные окружения, структура.
- [x] Исправить расхождение «9 таблиц» в документации и `database.types.ts` на фактическую схему (8 таблиц).
**Тесты:** `git status` чист после коммита; `npm run lint` и `npx tsc --noEmit` зелёные на закоммиченном состоянии.
**Когда готова:** критерии готовности PRD №3 и №5 — вся реализация в истории, README описывает запуск и env, учёт таблиц соответствует схеме.

### Фаза 3: Каскадное удаление пользователя

**Цель:** удаление пользователя администратором не оставляет «сирот» в БД.
**Затрагивает:** backend, database
**Задачи:**
- [x] Расширить `DELETE`-эндпоинт админки: удаление записи из `auth.users` через сервисную роль (`lib/supabase/admin.ts`).
- [x] Гарантировать каскадную очистку связанных данных: `profiles`, `projects`, `user_rates`, `user_service_hours`, `custom_services` (через транзакцию).
- [x] Сохранить существующие защиты: нельзя удалить себя.
**Тесты:** тест удаления на тестовой среде: после `DELETE` отсутствует запись в `auth.users`, нет осиротевших `profiles/projects`, повторный `GET` списка пользователей не содержит удалённого.
**Когда готова:** критерий готовности PRD №4.

### Фаза 4: Деплой на Vercel

**Цель:** приложение доступно в продакшене по публичному HTTPS-URL.
**Затрагивает:** инфраструктура (деплой)
**Задачи:**
- [ ] Развернуть проект на Vercel, настроить переменные окружения (Supabase URL/ключи).
- [ ] Применить миграции `supabase/migrations/` к продакшен-базе Supabase.
- [ ] Проверить продакшен: вход на `/dashboard` и создание проекта.
**Тесты:** smoke-сценарий на прод-URL: регистрация/вход → `/dashboard` → создание проекта; HTTPS активен.
**Когда готова:** критерий готовности PRD №6 — публичный URL работает, вход и создание проекта функционируют.
