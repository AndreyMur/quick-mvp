# Plan: Ядро расчёта v2

**PRD:** [docs/prd-calculation-engine-v2.md](prd-calculation-engine-v2.md)
**Дата:** 2026-09-09

## Фазы реализации

### Фаза 1: Чистое ядро без изменения поведения (Tracer Bullet)

**Цель:** расчёт отделён от чтения БД и стал тестируемым, при этом результаты совпадают с текущими.
**Затрагивает:** backend
**Задачи:**
- [ ] Выделить чистое расчётное ядро: вход — параметры проекта и справочники (ставки, нормативы, коэффициенты), выход — результат; убрать чтение Supabase изнутри расчёта.
- [ ] Перенести чтение данных (глобальные/пользовательские справочники, кастомные сервисы) на уровень вызывающего кода (API-роут).
- [ ] Сохранить равное распределение часов как поведение по умолчанию (эталон текущего алгоритма).
- [ ] Актуализировать типы и валидации (`lib/types/project.ts`, `lib/validations/calculate.ts`) под новую форму вызова.
**Тесты:** юнит-тесты на фиксированных наборах входных данных: результаты совпадают с эталонными значениями текущего алгоритма (регрессия); проверка кодом, что в чистом ядре нет обращений к Supabase.
**Когда готова:** критерий PRD №2 и фундамент №1/№5 — в ядре нет обращений к БД, `/api/calculate` работает с прежними результатами.

### Фаза 2: Распределение по весам и версия расчёта

**Цель:** пользователь может влиять на распределение часов по ролям; результат содержит версию алгоритма.
**Затрагивает:** backend
**Задачи:**
- [ ] Добавить во входные данные веса/задействованность ролей; распределять базовые часы пропорционально весам.
- [ ] Обеспечить: при равных весах результат идентичен текущему поведению.
- [ ] Обработать особые случаи: роль без ставки → стоимость 0; сумма весов = 0 обрабатывается явно без падения.
- [ ] Добавить версию алгоритма в результат расчёта.
**Тесты:** юнит-тесты сценариев из критерия №1 — равные веса дают прежний результат, неравные распределяют пропорционально, отсутствие ставки даёт 0, нулевая сумма весов не роняет расчёт.
**Когда готова:** критерий PRD №1 и часть №3 (версия в результате).

### Фаза 3: Совместимость снапшотов и контракта

**Цель:** старые сохранённые проекты и существующие клиенты не ломаются.
**Затрагивает:** backend
**Задачи:**
- [ ] Обеспечить корректное открытие на странице результата снапшота старого формата (без версии).
- [ ] Проверить совместимость `POST /api/calculate`, сохранения и пересчёта проекта без изменений контракта для клиентов.
- [ ] Синхронизировать OpenAPI-схему (`lib/openapi.ts`) с актуальным контрактом.
**Тесты:** тест открытия снапшота без версии; контрактные тесты API-вызовов со стороны страницы результата; `npm run lint` и `npx tsc --noEmit` без ошибок.
**Когда готова:** критерии PRD №3, №5 и №6.

### Фаза 4: UI весов ролей

**Цель:** пользователь задаёт задействованность ролей в конструкторе и видит её в результате.
**Затрагивает:** frontend
**Задачи:**
- [ ] Добавить на шаг 4 конструктора ввод весов/задействованности выбранных ролей.
- [ ] Сохранять веса в состоянии проекта; обеспечить совместимость со старым состоянием localStorage без весов.
- [ ] Отобразить веса/распределение по ролям на странице результата.
**Тесты:** тесты валидации шага (сумма весов > 0) и сохранения/восстановления состояния, включая старый формат без весов.
**Когда готова:** критерий PRD №4 — шаг 4 позволяет задать веса, данные сохраняются и корректно восстанавливаются.
