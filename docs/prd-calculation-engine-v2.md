# PRD: Ядро расчёта v2

**Дата**: 2026-09-09
**Статус**: Draft

## Цель

Повысить адекватность оценки стоимости/сроков и устранить архитектурные ограничения текущего ядра (`lib/calculate.ts`): равномерное распределение часов по ролям не отражает реальные проекты (риск зафиксирован в task-plan.md), функция читает БД напрямую изнутри (не тестируема и непредсказуема), а в результате нет версии алгоритма. Цель — сделать распределение часов настраиваемым по ролям, ядро чистым и тестируемым, а результаты — воспроизводимыми и версионируемыми.

## Пользовательские сценарии

- Пользователь на шаге 4 конструктора указывает, насколько каждая роль задействована (например, Frontend — большая часть работы, PM — малая) → расчёт распределяет часы сервисов пропорционально, а не поровну.
- Пользователь возвращается к сохранённому проекту через неделю → результат не «плывёт», если администратор менял глобальные ставки/коэффициенты: снапшот хранит версию параметров расчёта.
- Разработчик вносит изменение в алгоритм → прогоняет тесты на фиксированных наборах входных данных и видит, какие результаты изменились (ядро не зависит от состояния БД).
- API `/api/calculate` остаётся совместимым для клиентов (страница результата и конструктор не ломаются).

## В скоупе

- Введение настраиваемого распределения базовых часов по ролям (веса/степень задействованности роли) в шаге 4 конструктора; при равных весах результат идентичен текущему поведению.
- Выделение чистого расчётного ядра: вход — параметры проекта и справочники (ставки, нормативы, коэффициенты), выход — результат; чтение данных из БД выносится на уровень вызывающего кода.
- Версионирование расчёта: в результат и снапшот проекта включается версия алгоритма/параметров; отображение старых снапшотов не падает при изменении глобальных настроек.
- Обновление контракта: типы в `lib/types/project.ts`, валидации в `lib/validations/calculate.ts`, OpenAPI-схема в `lib/openapi.ts` синхронизируются с новым ядром.
- Точечные изменения UI шага 4 и страницы результата под веса ролей.

## Не в скоупе

- ИИ/эвристические оценки и бенчмарки против реальных проектов.
- Мультивалюта и курсы валют (в ТЗ — условные единицы).
- Сравнение проектов между пользователями и агрегатная аналитика.
- Пересчёт и миграция старых сохранённых проектов в новый формат (только совместимое отображение).

## Технические ограничения

- Существующий контракт `/api/calculate` и страницы результата завязаны на текущую структуру результата — менять с сохранением обратной совместимости.
- Распределение по весам не должно ломать особые случаи: роль без ставки → стоимость 0; сумма весов = 0 должна обрабатываться явно.
- `technology_coefficients` применяются к конкретным ролям через `TECH_ROLE_MAP` — логика коэффициентов сохраняется.
- Существующие данные `projects.data` содержат снапшоты старого формата без версии.

## Критерии готовности

- [ ] Юнит-тесты ядра покрывают: равные веса дают прежний результат (регрессия к текущему поведению), неравные веса распределяют часы пропорционально, отсутствие ставки у роли даёт 0, нулевая сумма весов не роняет расчёт.
- [ ] Расчёт не содержит прямых обращений к Supabase/БД внутри чистого ядра (справочники передаются параметром) — проверяется кодом и тестами.
- [ ] Результат расчёта содержит версию алгоритма; снапшот старого сохранённого проекта (без версии) корректно открывается на странице результата.
- [ ] Шаг 4 конструктора позволяет задать веса/задействованность ролей; данные сохраняются в состоянии проекта.
- [ ] `POST /api/calculate`, сохранение и пересчёт проекта на `/projects/[id]/result` работают без изменений контракта для клиентов.
- [ ] `npm run lint` и `npx tsc --noEmit` проходят без ошибок; OpenAPI-документация отражает актуальный контракт.
