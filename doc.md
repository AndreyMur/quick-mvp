# Техническое задание на разработку веб-приложения «MVP Calculator»

## 1. Введение

### 1.1. Наименование системы
Полное наименование: «MVP Calculator» — система автоматизированного расчета стоимости и сроков разработки MVP цифровых продуктов.

### 1.2. Цели и назначение разработки
**Цель:** Создать веб-инструмент, позволяющий менеджерам проектов, стартаперам и владельцам продуктов быстро оценить бюджет и временные рамки для создания MVP на основе выбираемых функциональных модулей и технологического стека.

**Основные задачи MVP-версии:**
- Предоставить публичный лендинг с описанием ценности продукта и возможностью регистрации.
- Реализовать личный кабинет пользователя с управлением сохраненными проектами.
- Реализовать панель администратора для управления пользователями, лимитами проектов и глобальными настройками.
- Обеспечить пошаговый конструктор расчета с выбором функциональных сервисов, технологий и состава команды.
- Генерировать детальную смету и оценку времени с возможностью экспорта в PDF и сохранения в базе данных.
- Предоставить страницу с тарифами (в первой версии активен только бесплатный план).
- Заложить архитектурную возможность добавления других языков в будущем.

### 1.3. Технологический стек
| Компонент        | Технология / Библиотека                                      |
|------------------|--------------------------------------------------------------|
| Фреймворк        | Next.js 14+ (App Router)                                     |

| UI-библиотека    | shadcn/ui (Radix UI + Tailwind CSS)                          |

| Хранилище файлов | Supabase Storage (для иконок кастомных сервисов)             |
| Деплой           | Vercel / собственный сервер с Node.js                        |

## 2. Пользовательские роли и права доступа

| Роль            | Права                                                                                     |
|-----------------|-------------------------------------------------------------------------------------------|
| **Посетитель**  | Просмотр лендинга, вход/регистрация.                                                       |
| **Пользователь**| Создание проектов в пределах лимита тарифа, редактирование/удаление своих проектов, просмотр расчетов, экспорт PDF, доступ к настройкам профиля и пользовательским нормативам. |

## 3. Функциональные требования

### 3.1. Модуль 1: Публичный лендинг
**Маршрут:** `/`

- Хедер с логотипом, навигационными ссылками (якоря на блоки лендинга) и кнопкой «Войти».
- Hero-секция с кратким УТП и кнопкой «Попробовать бесплатно».
- Блоки с описанием преимуществ (экономия времени, точность оценки, прозрачность).
- Футер с копирайтом и ссылками на политику конфиденциальности (заглушки).
- Форма входа/регистрации реализуется через Supabase Auth (email + пароль). После успешной аутентификации пользователь перенаправляется на дашборд `/dashboard`.

### 3.2. Модуль 2: Панель администрирования
**Маршрут:** `/admin`
Доступ разрешён только пользователям с флагом `is_admin = true`.

#### 3.2.1. Управление пользователями
- Таблица со списком всех зарегистрированных пользователей.
- Отображаемые колонки: Email, Дата регистрации, Текущий тариф, Лимит проектов, Количество созданных проектов, Статус администратора (is_admin).
- Возможность редактировать лимит проектов (`project_limit`) для любого пользователя.
- Возможность назначать/снимать права администратора (за исключением снятия прав у самого себя — защита от случайной блокировки).
- Возможность удалить пользователя (каскадное удаление его проектов и данных).

#### 3.2.2. Глобальные настройки
- **Ставки команды:** Форма с ролями (Project Manager, Frontend Developer, Backend Developer, Mobile Developer, QA Engineer, DevOps, UI/UX Designer) и полями для ввода часовой ставки в условных единицах.
- **Нормативы времени на сервисы:** Таблица стандартных сервисов с возможностью редактирования количества человеко-часов, необходимых для реализации каждого.
- **Коэффициенты технологий:** Таблица технологий (React, Vue, Angular, Node.js, Python, Ruby, PHP, PostgreSQL, MySQL, MongoDB, React Native, Flutter, Native iOS, Native Android) с возможностью задать коэффициент сложности (по умолчанию 1.0). Коэффициент применяется при расчёте к часам соответствующей роли.
- **Кастомные сервисы (глобальные):** Возможность добавить сервис, доступный всем пользователям (название, иконка, часы, фиксированная стоимость).

### 3.3. Модуль 3: Дашборд пользователя
**Маршрут:** `/dashboard`

- Приветствие по имени (если указано в профиле) или по email.
- Кнопка «Создать новый проект», ведущая на первый шаг конструктора (`/projects/new`).
- Индикатор использования лимита проектов (например, «Создано 2 из 3»).
- Список сохранённых проектов пользователя:
  - Карточка проекта содержит: название, дату создания, статус (черновик / завершён), итоговую стоимость и срок.
  - Действия с проектом: открыть результат, редактировать (возврат в конструктор с заполненными данными), удалить.
- Если лимит проектов исчерпан, кнопка создания нового проекта неактивна, при наведении показывается сообщение с предложением перейти на расширенный тариф.

### 3.4. Модуль 4: Настройки пользователя
**Маршрут:** `/settings`
Страница организована в виде вкладок или вертикального меню с секциями.

#### 3.4.1. Профиль
- Изменение отображаемого имени.
- Изменение пароля (через встроенный механизм Supabase).

#### 3.4.2. Зарплаты команды
- Форма для установки персональных часовых ставок для каждой роли.
- Если значение не задано, используется глобальная ставка из настроек администратора.

#### 3.4.3. Время на сервисы
- Таблица стандартных сервисов с возможностью указать собственную оценку в человеко-часах.
- Приоритет: если пользователь задал своё значение, используется оно; иначе — глобальное.

#### 3.4.4. Кастомные сервисы и скрытые платежи
- Форма для создания собственного сервиса.
- Поля: Название, Количество часов, Фиксированная стоимость (опционально).
- **Загрузка иконки:** Поле для выбора файла изображения (PNG, SVG). Иконка сохраняется в Supabase Storage в бакете `custom-service-icons` и отображается в конструкторе.
- Список созданных пользователем кастомных сервисов с возможностью редактирования и удаления.

#### 3.4.5. Коэффициенты технологий
- **Примечание:** В MVP данная секция доступна **только для просмотра**. Пользователь видит глобальные коэффициенты, установленные администратором, но не может их изменять. (Возможность персональных коэффициентов может быть добавлена в будущих версиях).

### 3.5. Модуль 5: Пошаговое создание проекта
**Маршрут:** `/projects/new` и `/projects/[id]/edit`
Конструктор реализован в виде последовательности слайдов (шагов) с индикатором прогресса. Состояние сохраняется в клиентском хранилище (Zustand / Context) до момента сохранения.

#### Шаг 1: Описательная часть
- Поле «Название проекта» (обязательное).
- Поле «Краткое описание» (опционально).
- Кнопка «Далее».

#### Шаг 2: Выбор функциональных сервисов
- Сетка из карточек (квадратные блоки: иконка + название).
- **Стандартные сервисы (MVP):**
  - Аутентификация пользователей
  - Личный кабинет
  - Платежная система
  - Чат (базовый)
  - Админ-панель
  - Уведомления (email/push)
  - Загрузка файлов
  - Аналитика
  - Интеграция с соцсетями
  - Поиск
- **Кастомные сервисы:** Отображаются в той же сетке, если пользователь их создал в настройках. Используется загруженная иконка.
- При клике на карточку она меняет цвет (активное/неактивное состояние).
- Кнопка «Далее».

#### Шаг 3: Выбор технологий разработки
- Радио-группы или выпадающие списки для выбора:
  - **Фронтенд:** React, Vue, Angular (по умолчанию React)
  - **Бэкенд:** Node.js, Python, Ruby, PHP (по умолчанию Node.js)
  - **База данных:** PostgreSQL, MySQL, MongoDB (по умолчанию PostgreSQL)
  - **Мобильная разработка:** React Native, Flutter, Native iOS, Native Android (если применимо)
- Кнопка «Далее».

#### Шаг 4: Состав команды
- Список ролей с чекбоксами:
  - Project Manager
  - Frontend Developer
  - Backend Developer
  - Mobile Developer
  - QA Engineer
  - DevOps
  - UI/UX Designer
- Для каждой выбранной роли — поле ввода количества человек (по умолчанию 1).
- Кнопка «Далее».

#### Шаг 5: Саммари и расчет
- Отображение сводной информации: название, выбранные сервисы (список), технологии, команда.
- Кнопка «Рассчитать».
- По нажатию отправляется запрос к API `/api/calculate`, который выполняет вычисления согласно алгоритму (раздел 7).
- После успешного расчета происходит переход на страницу результата.

### 3.6. Модуль 6: Подробный результат и экспорт
**Маршрут:** `/projects/[id]/result` (для сохранённых) или временная страница после расчёта.

- **Верхняя панель:**
  - Кнопка «Сохранить проект» — сохраняет все данные расчёта в БД, проект становится доступен в дашборде.
  - Кнопка «Экспорт в PDF» — инициирует скачивание файла.
- **Основная информация:**
  - Название проекта.
  - Итоговая стоимость (сумма).
  - Общее время в человеко-часах и ориентировочное календарное время (при указанном составе команды).
- **Детализация:**
  - Таблица сервисов: название, часы, стоимость.
  - Таблица по ролям: название роли, ставка, скорректированные часы, итоговая стоимость.
  - Отдельно выводятся фиксированные стоимости кастомных сервисов.
- **Визуализация:**
  - Круговая диаграмма распределения стоимости по ролям (опционально).
- **Примечание:** Для пользователей бесплатного тарифа в PDF-файл добавляется водяной знак «MVP Calculator Demo».

### 3.7. Экспорт в PDF
- Генерация выполняется на сервере (API Route) с использованием `@react-pdf/renderer`.
- Шаблон включает:
  - Заголовок с логотипом и датой формирования.
  - Сводные данные.
  - Таблицы с детализацией.
  - Подвал с пометкой «Сгенерировано в MVP Calculator».
- Файл отдаётся клиенту для скачивания; сохранение в облачное хранилище в MVP **не производится**.

### 3.8. Модуль 7: Подписки и тарифы
**Маршрут:** `/pricing`

- Страница отображает три тарифных плана в виде карточек.
  1. **Бесплатный (Free)** — активен по умолчанию.
     - Лимит проектов: **3**.
     - Доступ ко всем базовым функциям расчёта.
     - Возможность создания **до 2 кастомных сервисов**.
     - Экспорт PDF с водяным знаком.
  2. **Профессиональный (Pro)** — отображается, но кнопка неактивна (надпись «Скоро»).
     - Лимит: 20 проектов.
     - Без водяного знака.
  3. **Бизнес (Business)** — отображается, кнопка неактивна.
     - Безлимитные проекты.
     - Мультипользовательский доступ (в перспективе).
- В профиле пользователя отображается текущий тариф и использованный лимит.
- При попытке создать проект сверх лимита появляется модальное окно с предложением перейти на платный тариф.

### 3.9. Интернационализация (i18n)
- В MVP поддерживается только русский язык.
- Однако архитектура должна быть готова к добавлению других языков в будущем.
- Используется библиотека `next-intl`.
- Все текстовые строки выносятся в файлы локализации (`locales/ru/common.json`).
- В коде компонентов строки получаются через хук `useTranslations`.

## 4. Нефункциональные требования

### 4.1. Безопасность
- Аутентификация и авторизация через Supabase Auth.
- Включены Row Level Security (RLS) на все таблицы: пользователь видит только свои данные, администратор — все.
- Валидация входных данных на сервере с помощью Zod.
- Защита от CSRF (обеспечивается Next.js).
- Обязательное использование HTTPS.

### 4.2. Производительность
- Время ответа API расчёта — не более 2 секунд.
- Генерация PDF — не более 5 секунд.
- Использование React Server Components и кэширования где уместно для ускорения загрузки страниц.

### 4.3. Масштабируемость
- Архитектура должна позволять добавлять новые сервисы, роли, технологии и тарифы без значительной переработки ядра.

### 4.4. Интерфейс и дизайн
- Полное соответствие стилю shadcn/ui (поддержка светлой и тёмной темы).
- Адаптивная вёрстка: корректное отображение на десктопах и планшетах (мобильная версия не является приоритетом MVP, но интерфейс не должен ломаться).

### 4.5. Подготовка к мультиязычности
- Все пользовательские строки обёрнуты в механизм локализации.
- Даты и числа форматируются с учётом текущей локали.

| Поле        | Тип     | Описание                           |
|-------------|---------|------------------------------------|
| id          | uuid    | PK                                 |
| user_id     | uuid    | FK -> profiles.id                  |
| role        | text    |                                    |
| hourly_rate | integer |                                    |

### 5.6. Таблица `user_service_hours`
| Поле        | Тип     | Описание                           |
|-------------|---------|------------------------------------|
| id          | uuid    | PK                                 |
| user_id     | uuid    | FK -> profiles.id                  |
| service_key | text    |                                    |

| fixed_cost  | integer |                                    |

### 5.7. Таблица `custom_services`
| Поле        | Тип     | Описание                                                     |
|-------------|---------|--------------------------------------------------------------|
| id          | uuid    | PK                                                           |
| user_id     | uuid    | FK -> profiles.id (NULL для глобальных, созданных админом)   |
| name        | text    |                                                              |
| hours       | integer |                                                              |
| fixed_cost  | integer |                                                              |
| icon_url    | text    | Ссылка на файл в Supabase Storage                            |
| created_at  | timestamptz |                                                          |

### 5.8. Таблица `technology_coefficients`
| Поле            | Тип     | Описание                                 |
|-----------------|---------|------------------------------------------|
| id              | uuid    | PK                                       |
| technology_key  | text    | Уникальный ключ, например 'react'        |
| coefficient     | float   | По умолчанию 1.0                         |
| created_at      | timestamptz |                                      |
| updated_at      | timestamptz |                                      |

### 5.9. Политики RLS (Row Level Security)
- `profiles`: пользователи могут читать и обновлять только свою запись; администратор — все.
- `projects`: пользователи CRUD только свои проекты; администратор — все.
- `user_rates`, `user_service_hours`, `custom_services`: аналогично, пользователь работает только со своими записями; записи с `user_id = NULL` доступны всем для чтения.

### 5.10. Supabase Storage Buckets
- `custom-service-icons` — публичный бакет для хранения иконок кастомных сервисов.
- `pdf-exports` — (задел на будущее) приватный бакет для временных ссылок на PDF.

## 6. API эндпоинты (Next.js API Routes)

| Метод  | Путь                                        | Описание                                                         |
|--------|---------------------------------------------|------------------------------------------------------------------|
| POST   | `/api/auth/*`                               | Обработка колбэков аутентификации Supabase                       |
| GET    | `/api/user/profile`                         | Получить профиль текущего пользователя                           |
| PUT    | `/api/user/profile`                         | Обновить профиль                                                  |

## 7. Алгоритм расчета стоимости и времени

### 7.1. Входные данные
- Список выбранных сервисов (стандартные + кастомные).
- Выбранные технологии.
- Состав команды: роль → количество человек.

### 7.2. Последовательность расчета

1. **Определение базовых часов на сервисы:**
   - Для каждого выбранного стандартного сервиса берётся значение часов: пользовательское (если задано) → глобальное.
   - Для кастомных сервисов берутся часы, указанные пользователем.
   - Суммируются часы по всем сервисам → `total_base_hours`.

2. **Распределение часов по ролям:**
   - Используется равномерное распределение (MVP): все роли, задействованные в проекте, получают равную долю от `total_base_hours`.
   - Например, если выбраны роли Frontend, Backend, PM (3 роли), то каждая получает `total_base_hours / 3` часов.

3. **Применение коэффициентов технологий:**
   - Для каждой технологии определяется, на какие роли она влияет:
     - Фронтенд-технологии → Frontend Developer.
     - Бэкенд-технологии → Backend Developer.
     - Мобильные технологии → Mobile Developer.
     - База данных → Backend Developer (или выделенная роль DBA, если есть).
   - Часы соответствующей роли умножаются на коэффициент технологии.
   - Пример: выбрана технология React (коэф. 1.2), роль Frontend получила 40 часов → скорректированные часы = 40 × 1.2 = 48 часов.

4. **Расчёт стоимости:**
   - Для каждой роли определяется ставка: пользовательская → глобальная.
   - Стоимость роли = скорректированные часы × ставка.
   - Общая стоимость = сумма стоимостей всех ролей + сумма фиксированных стоимостей кастомных сервисов.

5. **Расчёт времени:**
   - Общее время в человеко-часах = сумма скорректированных часов по всем ролям.
   - Ориентировочное календарное время (дни) = общее время / (суммарное количество человек в команде × 8).

### 7.3. Особые случаи
- Если для роли не задана ставка (ни пользовательская, ни глобальная), стоимость этой роли считается равной 0.
- Если технология имеет коэффициент 0 — она не влияет на часы (но такая ситуация не рекомендуется).
- Фиксированные стоимости кастомных сервисов добавляются к итогу без умножения на ставки или коэффициенты.

## 8. Требования к реализации интерфейса

### 8.1. Компоненты и библиотеки
- Все интерактивные элементы строятся на базе shadcn/ui.
- Формы — `react-hook-form` с валидацией через `zod`.
- Пошаговый конструктор — кастомный компонент с управлением состоянием через Zustand или React Context, визуальный прогресс-бар.
- Диаграммы — `recharts`.
- Загрузка файлов — использование Supabase Storage API.

### 8.2. Визуальное оформление
- Использование Tailwind CSS для стилизации.
- Поддержка светлой и тёмной тем (переключатель в настройках профиля или в хедере).
- Адаптивность: на планшетах и десктопах интерфейс должен сохранять удобство использования; мобильная версия — базовая адаптация без потери функционала.

### 8.3. Особенности реализации пошагового конструктора
- Состояние шагов сохраняется в локальном хранилище браузера (localStorage) для предотвращения потери данных при обновлении страницы.
- Валидация обязательных полей перед переходом на следующий шаг.

## 10. Критерии приемки

- Посетитель может зарегистрироваться, войти и попасть на дашборд.
- Пользователь видит свой тариф (Бесплатный) и лимит проектов (3).
- Пользователь может создать проект в пределах лимита, пройти все шаги конструктора, рассчитать стоимость и время.
- Пользователь может сохранить проект, экспортировать результат в PDF (с водяным знаком).
- Пользователь может создать кастомный сервис с загрузкой иконки и использовать его в расчётах.
- Коэффициенты технологий, заданные администратором, корректно влияют на итоговый расчёт.
- Администратор может управлять пользователями, изменять лимиты, назначать других администраторов.
- Интерфейс соответствует стилю shadcn/ui, адаптивен.
- Все данные защищены политиками RLS.
- Код подготовлен к добавлению новых языков (строки вынесены в файлы локализации).
